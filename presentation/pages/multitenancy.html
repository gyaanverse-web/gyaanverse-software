Multi-Tenancy

Isolated by Design

Every coaching institute runs in its own fully isolated context — shared database, separate rows, zero data bleed. Tenant identity is resolved at the network edge and flows through every layer of the stack.

Routing Strategy

Subdomain Resolution

sharma.gyanverse.app strips to slug sharma, looks up the tenant row, and attaches it to req.tenant before any route handler fires.

Port is stripped first — sharma.app:3000 resolves identically to sharma.app. Local dev uses ?tenant=sharma as a fallback.

Isolation Model

Row-Level Isolation

No separate databases, no Postgres schemas — one shared pool, every query scoped by tenantId. Each tenant-scoped table carries a NOT NULL UUID foreign key referencing tenants.id.

Scoped tables: memberships, classes, classMembers, coachingJoinCodes, joinCodes, exams, evaluationJobs, tenantSettings

Data Segregation

Segregation Strategy

  • Shared pool — single Neon Postgres instance, single pg connection pool
  • FK enforcement — all tenant tables reference tenants.id at the DB level
  • Unique index — (userId, tenantId) unique index on memberships blocks duplicate joins at the DB level
  • Status gate — suspended tenants reject all student joins before any writes occur
  • Cascade teardown — deleting a tenant resets all member roles and purges all data in a single transaction

Provisioning Workflow

Atomic 4-Step Registration

POST /tenants  →  registerCoaching(ownerId, { slug, name })
  │
  ├─ Step 1 — Validate slug
  │     format check  →  /^[a-z0-9-]+$/  (lowercase, hyphens only)
  │     reserved list →  ['www', 'api', 'admin', 'app', 'static']  →  409 CONFLICT
  │     uniqueness    →  SELECT FROM tenants WHERE slug = ?         →  409 CONFLICT
  │
  ├─ Step 2 — Assert verified identity
  │     emailVerified OR phoneNumberVerified must be true
  │     neither verified  →  403 IDENTITY_NOT_VERIFIED
  │
  ├─ Step 3 — Assert single ownership
  │     SELECT FROM memberships WHERE userId = ? AND role = 'coaching_owner'
  │     already exists    →  409 CONFLICT  ("You already own a coaching")
  │
  └─ Step 4 — Atomic transaction  (all-or-nothing, 4 writes)
        INSERT tenants          →  tenant row with slug, name, plan='free'
        INSERT tenantSettings   →  1-to-1 settings row (same TX, always)
        INSERT memberships      →  owner row  { role: 'coaching_owner' }
        UPDATE users            →  role = 'coaching_owner', tenantId = <new id>
Security

Cross-Tenant Security Measures

Every tenant-scoped route runs a mandatory three-layer middleware chain before any handler or service code executes:

authenticate()
  └─ verify session cookie / token via Better Auth
  └─ attach { id, role } to req.user  →  401 if missing

tenantMiddleware()
  └─ extract slug from subdomain (or ?tenant= param)
  └─ SELECT FROM tenants WHERE slug = ?
  └─ attach full tenant row to req.tenant  →  404 if not found

requireTenantRole('coaching_owner' | 'teacher' | 'student')
  └─ fresh DB query every request — never cached
  └─ SELECT role FROM memberships
       WHERE userId = req.user.id AND tenantId = req.tenant.id
  └─ 403 FORBIDDEN if no row or role not in allowed list

Cross-tenant access is structurally impossible — the tenant on the request is always derived from the caller's own subdomain, not a user-supplied ID. A valid session for sharma.app returns 404 on gupta.app if no membership exists there.

Pro Feature

Custom Domain Routing

Pro plan tenants can register a custom domain (e.g. portal.sharmainstitute.in) stored in tenantSettings.customDomain.

Gated by assertHasFeature('custom_branding') in the service layer before the DB write — route handlers never contain plan logic.
