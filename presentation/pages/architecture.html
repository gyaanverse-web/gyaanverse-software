Architecture

Modular Monolith

One deployable, many independent modules. Each feature owns its schema, types, service, and routes — ready to extract into a microservice without rewriting anything.

Multi-tenancy

Row-level isolation

Every tenant-scoped table carries a tenantId FK. The tenant middleware resolves the subdomain to a tenant row on every request and attaches it to request.tenant.

In local dev, ?tenant=slug substitutes for the subdomain.

Request flow

How a request moves through the system

Client (web / mobile)
  │
  ▼
Fastify HTTP API  (src/server.ts)
  │  auth.middleware    →  verify session token or cookie, attach user
  │  tenant.middleware  →  resolve subdomain → tenant row, attach tenant
  │
  ├── Global routes    (auth, billing, super-admin)
  └── Tenant routes    (classes, members, invites, …)
        │
        ▼
    Service layer  (pure business logic — no HTTP concerns)
        │
        ├── Drizzle ORM  →  Neon Postgres
        ├── BullMQ queue →  Redis  →  Worker process (src/worker.ts)
        └── Cloudflare R2           (file upload / signed URLs)
Async workers

BullMQ + Redis

A separate src/worker.ts process consumes queues from Redis. Jobs include email delivery, OTP dispatch, and exam orchestration. The worker shares the same Drizzle connection and services — no code duplication.

Plan & feature gating

Enforced at the service layer

Limits are thrown as structured errors — Errors.PLAN_LIMIT() or Errors.FEATURE_GATED() — exclusively in services, never in route handlers.

Authentication

  • Email + password — verification required before first login
  • Phone OTP — MSG91 (logs to console if keys absent in dev)
  • authenticate() — verifies session token or cookie
  • requireRole() — checks global user role
