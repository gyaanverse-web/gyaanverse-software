Module 01 — Auth

Identity & Sessions

  • Email + password — sign-up, sign-in, email verification required before first login, password reset flow
  • Phone OTP — MSG91 in production, console-logged in dev for zero external dependencies during development
  • Sessions — secure HttpOnly cookie and Bearer token (for mobile clients), both handled by Better Auth
  • Profile — name, phone, email; phone-only accounts can upgrade to email later without losing their session
  • Dual identity path — phone users get a synthetic @phone.gyanverse.app email internally; real email added via a verified upgrade flow

Module 02 — Tenant

Coaching Institute Management

  • Registration — any verified user registers a coaching with a unique slug; becomes the coaching_owner in one atomic transaction
  • Slug rules — lowercase, alphanumeric + hyphens; reserved words (www, api, admin, app, static) blocked
  • Teacher management — owner adds teachers by phone number; plan limits enforced before insert
  • Student joins — direct join by tenant ID or via shareable join code
  • Branding — logo URL; Pro plan unlocks custom domain via tenantSettings
  • Cascade delete — removing the institute resets all member roles and purges all data atomically

Module 03 — Class

Classes & Enrolment

  • Class CRUD — teachers create and own their classes; owners can manage any class within their institute
  • Join codes — each class generates multiple codes with optional expiry and max-use cap
  • Auto-approve toggle — new students are either approved instantly or held in pending status for teacher review
  • Approval workflow — teacher reviews pending enrolments and approves or rejects; rejected students can re-request
  • Role-aware listing — students see only approved classes; teachers and owners see all
  • Membership prerequisite — student must belong to the coaching before joining any of its classes
13 routes 3 DB tables
Module 04 — Membership

Coaching Join Codes

  • Shareable codes — 8-character uppercase codes; deliberately excludes 0 O 1 I to prevent misreading
  • Public preview — unauthenticated endpoint returns coaching name and logo before committing to join
  • Authenticated join — inserts membership and sets users.tenantId in a single transaction; plan limit checked first
  • Lifecycle controls — owner can revoke codes; codes expire by date or max-use count
  • Uniqueness guarantee — (userId, tenantId) unique index at DB level; duplicate joins caught at app layer first
5 routes 2 DB tables
Module 05 — Invite

Teacher Invitations

  • Token-based — 32-char hex token (UUID without hyphens), stored in DB, delivered via email or SMS
  • 48-hour TTL — invites expire automatically; acceptance after expiry is rejected
  • Contact verification — teacher's verified email or phone must match the invite's contact before acceptance proceeds
  • Lifecycle — pending → accepted (on use) or revoked (by owner); terminal states cannot be undone
  • Duplicate guard — only one pending invite per contact per tenant at a time
  • Dev mode — email and SMS payloads logged to console; no external service required during development
4 routes 1 DB table
Module 06 — Billing

Plan Enforcement

  • Centralised gatekeeping — all limit and feature checks live exclusively in billing.service.ts; route handlers never contain plan logic
  • Live usage counts — student, teacher, class, mock, and AI evaluation quotas are counted from the DB on each operation — no cached counters that drift
  • assertWithinLimit(tenantId, limit) — throws PLAN_LIMIT before any write if at or over quota
  • assertHasFeature(tenantId, feature) — throws FEATURE_GATED if the tenant's plan does not include the requested feature
  • Razorpay webhooks — subscription events upgrade or downgrade the plan stored on the tenant row

Class Enrolment Flow

From Code to Classroom

A student joining a class goes through a layered workflow designed to give teachers full control without adding friction for institutes that want open enrolment:

  1. Teacher generates a class join code (optional expiry + max-use cap)
  2. Student hits GET /tenant/classes/join/:code — previews class name and institute, no auth required
  3. Student posts to POST /tenant/classes/join/:code with a valid session
  4. System checks: student is a coaching member → plan class limit → code is valid and unexpired
  5. autoApprove = true → enrolment inserted as approved, student can access class immediately
  6. autoApprove = false → enrolment inserted as pending, teacher reviews via PATCH /tenant/classes/:id/students/:studentId
Access Control

Role Hierarchy

  • super_admin — platform-level, all tenants
  • coaching_owner — full control of their institute, classes, and members
  • teacher — manages their own classes and enrolments within the institute
  • student — reads approved class content, joins via codes

Global role lives on users.role. Tenant role is always read live from the memberships table — revocations take effect on the next request with no cache to invalidate.
